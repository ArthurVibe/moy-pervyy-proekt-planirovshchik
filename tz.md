# Техническое задание: What's Up, Bro? — браузерный прототип

Версия ТЗ: 1.2 — согласованы рекомендации по визуальному стилю. Статус: требования для реализации; код приложения ещё не написан.

## 1. Назначение и приоритет требований

Разработать простой персональный планировщик для проверки группировки по срокам, быстрого последовательного добавления и сохранения задач в браузере. Основной цикл: создать задачу → при необходимости назначить срок → выполнить → вернуться к сохранённому списку.

Это самодостаточное ТЗ: для реализации не требуется доступ к другим документам. Оно учитывает `concept.md`, приложенный ранее Roadmap v4.0 и последующие ответы пользователя; при расхождениях по поведению прототипа приоритет имеет это ТЗ. Дорожная карта — контекст дальнейшего развития, не источник дополнительных требований. Её версию не переименовывать в v1.0: это другой документ.

Прототип проверяет три вопроса: понятна ли группировка задач по датам и просрочке; удобно ли быстро вводить несколько дел на один день; сохраняются ли задачи между открытиями на целевых браузерах, особенно Safari на iPhone. Он не проверяет качество будущего AI-ввода. Ручная форма служит способом создать данные для этих проверок, а не утверждённым интерфейсом будущего AI.

Компоновка прототипа не является финальным референсом для будущего MVP. Одна колонка и отсутствие маскота/приоритетов выбраны только для этого эксперимента. Общий визуальный характер согласован отдельно: графитовые поверхности, единый зелёный акцент, мягкие скругления и спокойная типографика (раздел 15).

Пользователь подтвердил:

- Windows: Chrome и Firefox; iPhone: Safari.
- Один общий список без фильтров.
- Группы «Просрочено», «Сегодня», «Завтра», конкретные даты, «Без даты».
- Прошедшие сроки разрешены. Задача только с датой просрочена со следующего дня; с датой и временем — с наступления указанного времени.
- Выполненные хранятся до ручного удаления в нижнем сворачиваемом блоке, доступны для редактирования и возврата в работу.
- Одинаковые названия запрещены.
- После добавления сохраняется выбранная дата для быстрого ввода следующих задач.
- Нейтральные кнопки; характер продукта передают название и приветствие.

Остальные решения ниже фиксируют поведение реализации без необходимости дополнительных продуктовых согласований. В частности, уникальность названий распространяется и на выполненные задачи, а после добавления сохраняется только дата, не время.

### 1.1. Приоритеты и результат проверки

- Обязательно: сценарии задач, даты и группировка, сохранение без потери данных, обработка ошибок, доступность основных действий, проверки ключевой логики и отчёт о целевых браузерах. Защита от последовательных конфликтов вкладок остаётся обязательной: она предотвращает потерю уже введённого списка.
- Желательно: дополнительная визуальная полировка отступов и типографики в заданной теме. Она не расширяет функциональность и не задерживает проверку рабочих сценариев.
- Позже: функции раздела 19 и проверка гипотез об AI/полном интерфейсе MVP. NFKC-нормализация и искусственная монотонность времени изменения для прототипа не нужны.

После тестирования записать в README результаты по трём вопросам выше, замеченные неудобства и проверенные браузеры/способы запуска. Не делать вывод о надёжности многомесячного хранения по одному короткому тесту.

## 2. Объём поставки и ограничения

Приложение состоит ровно из трёх файлов в каталоге `prototype/`:

| Файл | Назначение |
| --- | --- |
| `prototype/index.html` | Семантическая разметка и подключения CSS/JS |
| `prototype/style.css` | Все стили, адаптивность, состояния фокуса и ошибок |
| `prototype/script.js` | Данные, localStorage, даты, проверки, действия и отображение |

`concept.md`, `tz.md` и README являются документацией и не входят в эти три файла приложения. Тестовые файлы `tests/*.test.cjs` находятся вне `prototype/` и не загружаются браузером. Дополнительные изображения, шрифты, библиотеки, файлы данных и зависимости приложения не нужны. Простые иконки допустимы как встроенный SVG в HTML, с текстовой подписью или доступным именем.

Код прототипа изолирован от будущего каркаса MVP и может быть заменён после проверки. Не обещать его автоматический перенос в React/TypeScript. Сам прототип и его данные после эксперимента не удалять автоматически; повторное использование правил и миграция данных — отдельная задача. Для этого ТЗ не создавать каркас будущего MVP.

Технологии: обычные HTML5, CSS и JavaScript. Подключение JS — обычным скриптом с `defer`, без `type="module"`. Для запуска приложения не нужны сборка, npm, Node.js, CDN, фреймворки, API, серверная логика, cookies и база данных. Node.js используется только разработчиком для автономных тестов (раздел 18). Скрипты и стили приложения размещать в соответствующих файлах, без inline-обработчиков событий.

Все пользовательские данные находятся в localStorage. Действия не отправляют текст задач и другую информацию в сеть. Не подключать аналитику, внешние шрифты и сетевые ресурсы.

## 3. Пользователь

Один пользователь — владелец браузерного профиля; ему доступны все действия раздела 5, без регистрации и ролей. Доступ к профилю означает доступ к его задачам. Между профилями, браузерами, устройствами и разными адресами страницы данные не переносятся и не синхронизируются, в том числе при открытии одного HTTPS-адреса на компьютере и iPhone.

## 4. Экран приложения

Один экран, одна колонка, без маршрутизации, вкладок, боковых панелей и отдельных разделов.

Порядок элементов:

1. Название `What's Up, Bro?` и приветствие «Привет! Что запланируем?».
2. Постоянное пояснение небольшим текстом: «Задачи сохраняются только в этом браузере. Очистка данных сайта удалит список».
3. Область системных сообщений: состояние хранилища, ошибки, результаты действий.
4. Форма создания или редактирования задачи.
5. Группы невыполненных задач.
6. Сворачиваемый блок «Выполненные · N», если выполненные задачи существуют.

Нет переключателей «Все / Сегодня» и иных фильтров. Все невыполненные задачи доступны в общем списке. Заголовки групп не являются кнопками и не скрывают задачи.

### 4.1. Форма

| Элемент | Поведение |
| --- | --- |
| «Задача» | Однострочное текстовое поле; обязательно; максимум 200 символов по правилам раздела 6 |
| «Дата» | Необязательный `input type="date"` |
| «Время» | Необязательный `input type="time"`, шаг 1 минута; недоступен без даты |
| «Без даты» | Кнопка явно очищает дату и время; недоступна, когда оба поля уже пусты |
| «Добавить» | Основное действие в режиме создания |
| «Сохранить» и «Отмена» | Действия в режиме редактирования вместо «Добавить» |

Все поля имеют видимые подписи. Placeholder не заменяет подпись. Под временем — пояснение «Сначала выберите дату». Необязательность даты и времени должна быть понятна из подписей или общей подсказки.

При первом открытии поля пусты: дата не подставляется автоматически. На телефоне не открывать клавиатуру без действия пользователя. Нажатие Enter в поле названия отправляет активную форму; Enter во время IME-композиции не отправляет её. Основная кнопка всегда остаётся доступным способом отправки.

Форма находится в обычном потоке страницы, без `sticky`/`fixed`: на iPhone она не должна занимать экран поверх длинного списка и клавиатуры. Отдельная плавающая кнопка добавления не требуется. При «Изменить» приложение само прокручивает к форме; возврат к карточке описан в разделе 10.

### 4.2. Карточка задачи

Содержит checkbox выполнения, полный текст названия, дату/время при наличии, кнопки «Изменить» и «Удалить». Название переносится по строкам, включая длинные слова, без обрезки, потери текста и горизонтального скролла.

Дата выводится с днём недели: `Чт, 22.10.2026`, время — в 24-часовом формате `ЧЧ:ММ`. Дни недели вычисляются для даты, а не задаются вручную. Сокращения: Вс, Пн, Вт, Ср, Чт, Пт, Сб. Для задачи с датой без времени показывается «Без времени»; для задачи без даты — «Без даты». В просроченной карточке видна текстовая метка «Просрочено», а не только цвет.

Нажатие на название не переключает выполнение и не открывает редактирование. Выполнение меняется только checkbox. Элементы действий доступны постоянно, включая сенсорные устройства.

### 4.3. Пустые состояния

- При отсутствии любых задач: «Пока нет задач. Добавьте первую выше».
- Если есть только выполненные: «Все задачи выполнены. Можно добавить новую» и блок выполненных ниже.
- Пустые группы дат и блок выполненных с нулевым количеством не показываются.
- При ошибке загрузки хранилища не показывать обычное пустое состояние как будто данных нет; вместо него показать состояние ошибки.

## 6. Название и запрет дубликатов

Перед проверкой и сохранением названия удалить пробелы по краям и заменить каждую последовательность пробельных символов одним обычным пробелом. Сохранять регистр букв пользователя. HTML и переносы строк не интерпретируются как разметка; вставленные переносы превращаются в пробелы.

После такой обработки допустимо от 1 до 200 Unicode-кодовых точек включительно: эмодзи из одной суррогатной пары не считается двумя символами. Не обрезать длинное название молча: показать ошибку. Точный алгоритм подсчёта приведён в разделе 16.1.

Названия сравниваются без учёта регистра и лишних пробелов. Дополнительное преобразование Unicode NFKC не выполнять. Пунктуацию и буквы не удалять; «е» и «ё» считать разными буквами. Алгоритм сравнения зафиксирован в разделе 16.1.

Уникальность проверяется среди всех задач, включая выполненные, независимо от даты и времени. Примеры: «Позвонить клиенту», « позвонить  клиенту » и «ПОЗВОНИТЬ КЛИЕНТУ» считаются одним названием. «Позвонить клиенту А» и «Позвонить клиенту Б» — разными.

При редактировании исключать из сравнения саму редактируемую задачу по id. Изменение только регистра своего названия допустимо. При совпадении ничего не сохранять, фокусировать название и показывать:

- Для активной записи: «Задача с таким названием уже есть. Измените название или отредактируйте существующую».
- Для выполненной записи: «Задача с таким названием уже есть среди выполненных. Верните её в работу или измените название».

Дубликат не заменяет существующую запись и не создаёт вторую. После удаления записи её название можно использовать снова.

Ограничение среди выполненных сохранено сознательно: пользователь запретил одинаковые названия, а повторяющиеся дела не входят в эту версию. Для нового одноимённого дела можно вернуть прежнюю задачу в работу и изменить срок либо удалить прежнюю запись. Не ослаблять правило до «только активные» без нового решения пользователя.

## 7. Даты, время и просрочка

### 7.1. Формат и допустимые значения

- `dueDate`: `null` или валидная григорианская календарная дата `YYYY-MM-DD` в диапазоне 2000-01-01–2099-12-31. Это явная граница тестового планировщика, не ограничение HTML. В форме задать соответствующие `min`/`max`; при загрузке и отправке проверять реальность дня, високосного года и диапазон.
- `dueTime`: `null` или строка `HH:mm`, часы 00–23, минуты 00–59. Секунды не хранятся.
- Время без даты запрещено и на уровне формы, и на уровне модели данных.
- Прошедшие даты и время допустимы; предупреждение не блокирует добавление.
- Изменение заполненной даты на другую сохраняет введённое время. Очистка даты немедленно очищает время в форме и делает его недоступным.

Дата и время задачи — местные календарные значения, не UTC-момент. Не извлекать текущий день через `toISOString().slice(0, 10)`. Использовать локальные компоненты браузерного времени. «Завтра» вычислять прибавлением календарного дня, не фиксированных 24 часов.

При смене часового пояса компьютера/телефона значения задачи не сдвигаются: «10:00» остаётся «10:00» в новом местном часовом поясе. Группировка пересчитывается. Отдельной настройки часового пояса нет.

### 7.2. Определение просрочки

Просрочка — вычисляемое состояние, в localStorage отдельным полем не записывается. Выполненные задачи никогда не считаются просроченными.

Для невыполненной задачи:

1. Без даты — не просрочена.
2. Дата раньше местного сегодняшнего дня — просрочена независимо от времени.
3. Дата позже сегодняшнего дня — не просрочена.
4. Дата сегодня, время отсутствует — не просрочена до смены дня.
5. Дата сегодня и время задано — просрочена, когда текущие локальные часы/минуты достигли или превысили указанное время. Например, задача на 10:00 просрочена с 10:00:00.

Сравнение времени внутри текущего дня выполняется по календарным часам/минутам. В переходы летнего времени не изобретать отдельный UTC-сдвиг задачи; это прототип без напоминаний.

Перемещение сегодняшней задачи в «Просрочено» в момент наступления её времени — сознательно сохранённое согласованное поведение. Льготного интервала и отдельного статуса «началась» нет. При фоновом перемещении сохранять фокус на том же элементе задачи по id, если он был внутри карточки, и не выполнять программную прокрутку. Автообновление не должно сбрасывать фокус в начало страницы.

## 8. Группировка и сортировка

Каждая активная задача должна находиться ровно в одной группе. Выполненные не участвуют в этих группах.

Порядок групп:

1. «Просрочено» — все активные задачи, подходящие под раздел 7.2, включая задачи сегодняшнего дня с уже наступившим временем.
2. «Сегодня · Вт, 20.10.2026» — остальные задачи на текущий день (дата и день недели вычисляются).
3. «Завтра · Ср, 21.10.2026» — задачи на следующий календарный день (дата и день недели вычисляются).
4. Отдельные группы остальных будущих дат по возрастанию; заголовок вида `Чт, 22.10.2026`.
5. «Без даты».
6. Нижний отдельный сворачиваемый блок «Выполненные · N».

Даты в примерах предполагают, что сегодня 20.10.2026. При другой текущей дате заголовки меняются автоматически. «Сегодня» и «Завтра» далее в тексте и проверках означают эти группы вместе с вычисляемой подписью даты.

Внутри каждой активной группы сортировать по дате по возрастанию, затем по времени по возрастанию; отсутствие времени идёт после заданного времени для той же даты. При равенстве использовать `createdAt` по возрастанию, затем id лексикографически для стабильности. В группе «Без даты» — `createdAt`, затем id.

Выполненные сортировать по `updatedAt` по убыванию, затем `createdAt` по возрастанию и id. Специальное поле времени выполнения не требуется; редактирование выполненной записи может поднять её в этом блоке.

При каждой загрузке блок выполненных свёрнут. В течение сеанса сохранять его положение при обновлении списка. Добавление новой выполненной записи не раскрывает блок автоматически. При исчезновении последней выполненной записи блок убирается; при его повторном появлении начинается свёрнутым. Состояние раскрытия в localStorage не хранить.

Обновлять группировку после успешного действия, при возврате фокуса/видимости страницы и таймером у ближайшей границы минуты. После каждого срабатывания вычислять задержку до следующей границы заново. На скрытой странице таймер можно приостановить. При возвращении во вкладку выполнить пересчёт сразу. Пересчёт не отправляет уведомлений, не меняет `updatedAt`, не записывает localStorage и не очищает форму, ошибки ввода или фокус.

## 9. Создание и быстрый последовательный ввод

Порядок операции: прочитать поля → нормализовать и проверить → проверить актуальность хранилища → создать новый объект и кандидат полного состояния → записать кандидат → только при успехе заменить текущее состояние интерфейса.

Новая задача имеет новый id, `completed: false`, одинаковые `createdAt` и `updatedAt`, а незаданные дату/время — как `null`.

После успешного добавления:

- Показать «Задача добавлена».
- Очистить название и время; оставить именно выбранную дату, включая пустую.
- Вернуть фокус в название для следующего ввода, без прокрутки к созданной карточке.
- Обновить нужную группу; не менять положение остальных элементов без необходимости.

Запоминание даты действует только в текущем открытии страницы. После перезагрузки форма вновь пустая. Выбор даты не записывается в настройки. Если день сменился, оставленная в форме дата не подменяется автоматически.

При ошибке поля или записи все значения формы остаются. Повторное нажатие не создаёт две записи: на время обработки отправка защищена флагом выполнения и недоступной кнопкой. После успешной синхронной записи пустое название предотвращает повторную отправку.

## 10. Редактирование

Используется та же верхняя форма, явно обозначенная заголовком «Редактирование задачи». При входе сохранить черновик создания только в памяти и заполнить поля данными выбранной задачи. При нажатии «Изменить» перевести фокус в название и обеспечить видимость формы.

Одновременно редактируется одна задача. Пока открыт редактор, checkbox, «Изменить» и «Удалить» всех карточек недоступны. Это исключает потерю текущего редактирования и удаление редактируемой записи. Чтение списка и раскрытие выполненных доступны.

«Сохранить» применяет те же проверки, что создание, включая уникальность с исключением собственного id. Сохраняются id, `createdAt` и `completed`; меняются только поля формы и `updatedAt` при фактическом изменении. Если нормализованные значения не отличаются, не писать хранилище, завершить редактирование с сообщением «Изменений нет».

После успешного сохранения или «Отмены» вернуться к созданию и восстановить прежний черновик, включая его дату и время. Отмена не пишет хранилище. При ошибке сохранения остаться в редакторе со всеми введёнными значениями.

После сохранения, «Изменений нет» или «Отмены» вернуть фокус на кнопку «Изменить» той же задачи по id. Если карточка после переноса срока оказалась вне видимой области, прокрутить к ней минимально необходимым образом (`scrollIntoView` с `block: 'nearest'`, без анимации). Если отредактированная задача выполнена, сохранить её блок раскрытым, чтобы кнопка оставалась доступной. Это правило имеет приоритет над возвратом фокуса в поле названия, который применяется только после создания. При сохранении с ошибкой фокус остаётся в форме по правилам раздела 14.

Изменение срока выполненной задачи не возвращает её в работу. Для этого пользователь отдельно снимает checkbox. Перезагрузка страницы теряет несохранённые черновики; автосохранения ввода и обработчика `beforeunload` нет.

## 11. Выполнение и удаление

### 11.1. Выполнение / возврат

Checkbox изменяет только `completed` и `updatedAt`. Срок, название, id и дата создания сохраняются. Новый статус отображается после успешной записи. При ошибке вернуть checkbox к предыдущему состоянию, не перемещать карточку и показать сообщение.

После выполнения сообщать «Задача выполнена». После снятия отметки — «Задача возвращена в работу». Возвращённая задача может сразу оказаться просроченной согласно текущему времени.

Если карточка исчезла из текущего места после выполнения, фокус переводится на checkbox следующей видимой задачи; если её нет — предыдущей. Если нет видимых задач, фокусировать заголовок блока выполненных при его наличии, иначе поле названия. Возврат из выполненных направляет фокус на checkbox перемещённой активной задачи.

### 11.2. Удаление

Для простоты использовать нативный `window.confirm` с текстом `Удалить задачу «{название}»? Это действие нельзя отменить.` Название подставляется как обычная строка, без HTML.

Отказ ничего не меняет. Подтверждение удаляет ровно выбранный id; состояние интерфейса изменяется только после успешной записи. При успехе — «Задача удалена», при неудаче задача остаётся на месте. Возврат фокуса после удаления — к следующей, затем предыдущей видимой задаче; если их нет — к названию в форме.

Корзины, массового удаления и отмены после подтверждённого удаления нет. Активные и выполненные задачи удаляются одинаково.

## 12. Модель данных

Единственный ключ приложения: `whats-up-bro.storage`. Не читать и не изменять чужие ключи. Не использовать `localStorage.clear()`.

Формат JSON:

```json
{
  "schemaVersion": 1,
  "tasks": [
    {
      "id": "a-unique-generated-id",
      "title": "Позвонить поставщику",
      "dueDate": "2026-10-20",
      "dueTime": "10:00",
      "completed": false,
      "createdAt": "2026-10-18T09:00:00.000Z",
      "updatedAt": "2026-10-18T09:00:00.000Z"
    }
  ]
}
```

Это пример структуры, не начальные данные приложения. На первом открытии массив пустой.

| Поле | Ограничения |
| --- | --- |
| `schemaVersion` | Целое число, строго `1` |
| `tasks` | Массив валидных задач |
| `id` | Непустая строка, уникальная внутри массива; при создании — UUID через `crypto.randomUUID`, при недоступности — UUID на основе `crypto.getRandomValues` |
| `title` | Строка в сохранённом нормализованном виде по разделу 6, уникальная по ключу сравнения |
| `dueDate` | Валидная дата или `null`; поле обязательно присутствует |
| `dueTime` | Валидное время или `null`; поле обязательно присутствует; без даты только `null` |
| `completed` | Строго boolean |
| `createdAt`, `updatedAt` | Валидные канонические строки UTC ISO 8601 вида `YYYY-MM-DDTHH:mm:ss.sssZ` |

При изменениях `createdAt` сохраняется. Новый `updatedAt` — фактическое текущее UTC-время. Искусственно увеличивать метку при переводе часов назад не нужно; при загрузке не требовать `updatedAt >= createdAt`. Обе метки обязаны быть валидными каноническими ISO-строками. Сортировка по ним остаётся детерминированной, но не обещает восстановить фактическую хронологию после ручного перевода системных часов.

У каждого объекта должны быть все перечисленные поля и не должно быть неизвестных полей: неизвестную структуру нельзя молча переписать и потерять. В схеме нет настроек, приоритетов, заметок, напоминаний, описаний и повторений. Данные формы и вычисляемые группы не сохраняются.

## 13. Хранилище, ошибки и конфликт вкладок

### 13.1. Загрузка

Чтение localStorage и парсинг всегда внутри `try/catch`.

- Ключ отсутствует (`getItem` вернул `null`): принять пустое валидное состояние в памяти. Не писать пустой объект до первого изменения.
- Ключ существует: разобрать JSON и проверить весь объект, каждую запись, уникальность id и названий, взаимосвязь полей и версию.
- Пустая строка, неверный JSON, неверные поля, дубликаты или неизвестная версия — ошибка загрузки всего набора. Не выкидывать отдельные записи и не заменять набор пустым.
- При неизвестной версии миграцию не угадывать: показать «Эта версия данных не поддерживается. Данные не изменены».
- При прочих повреждениях показать «Не удалось прочитать сохранённые задачи. Данные не изменены».
- При отказе доступа показать «Хранилище браузера недоступно. Сохранение задач невозможно».

В состоянии ошибки загрузки блокировать форму и действия изменения, не показывать ложный пустой список. Доступна кнопка «Повторить загрузку». Исходную строку не логировать и не удалять. Автоматического восстановления, сброса и UI для ручного исправления JSON нет. После устранения причины повторная загрузка снова читает данные.

Если ключ удалось прочитать, но JSON/схема не прошли проверку, дополнительно дать кнопку «Скопировать сохранённые данные». Она копирует точную исходную строку, полученную при неудачной загрузке, без парсинга, форматирования или перезаписи. Это аварийное извлечение, не штатный экспорт задач. Копирование запускается только пользователем и не отправляет данные в сеть.

При доступности Clipboard API использовать его и показывать «Исходные данные скопированы» только после успешного завершения. Если API недоступен или запрос отклонён, показать readonly textarea с исходной строкой и подсказкой «Выделите текст и скопируйте его вручную», перевести туда фокус; разрешить штатное выделение/копирование на iPhone. Содержимое устанавливать через `value`, не `innerHTML`. Отдельная кнопка «Скрыть исходные данные» убирает textarea и возвращает фокус на кнопку копирования. Если само чтение localStorage не удалось или ключ отсутствует, исходной строки нет и кнопка не показывается. Аварийное копирование также доступно для неизвестной версии или неизвестных полей; изменение данных при этом остаётся заблокированным.

### 13.2. Запись и отказ сохранения

Для каждого изменения сначала сформировать новое состояние отдельно от текущего и сериализовать его. Один полный JSON записывается одним `setItem`. Только после успешного вызова кандидат становится состоянием приложения. Ошибка записи не должна оставлять несохранённые изменения видимыми как сохранённые.

Сообщение по умолчанию: «Не удалось сохранить изменения. Данные не изменены. Повторите попытку». При `QuotaExceededError`: «В хранилище браузера недостаточно места. Изменения не сохранены». Не очищать приложение или другие данные браузера ради освобождения места.

Сохранённый список остаётся доступен. Ввод и редактирование сохраняют черновик; выполнение и удаление оставляют прежнюю карточку. Следующее явное действие пользователя может повторить запись. Если доступ к хранилищу потерян, не продолжать работу в скрытом режиме «только в памяти».

### 13.3. Несколько вкладок

Основной сценарий — одна вкладка. Перед каждой записью проверять, что сохранённые данные не изменились с момента загрузки этой вкладкой, по алгоритму раздела 16.4. При несовпадении не писать, даже если событие `storage` ещё не пришло.

Также отслеживать `storage` для ключа приложения и очистки хранилища (`event.key === null`), и проверять актуальность при возвращении фокуса/видимости. Изменения посторонних ключей игнорировать.

При обнаружении внешнего изменения блокировать новые изменения и показать: «Данные изменены в другой вкладке. Загрузите актуальный список. Несохранённый ввод будет потерян». Существующие черновики до перезагрузки остаются видны, чтобы текст можно было скопировать. Кнопка «Загрузить актуальные данные» явно сбрасывает черновики, выходит из редактора и читает текущее хранилище. При успехе форма пустая, выполненные свёрнуты. При ошибке применить раздел 13.1.

Не реализовывать автоматическое слияние. localStorage не даёт атомарной транзакции между чтением и записью в разных вкладках: абсолютная защита от строго одновременных записей не является обещанием прототипа. Последовательные внешние изменения должны обнаруживаться описанной проверкой.

## 14. Сообщения и проверки формы

Ошибки полей выводить рядом с соответствующим полем с привязкой через `aria-describedby` и `aria-invalid`. Фокус переводить к первому ошибочному полю в порядке: название, дата, время. Исходный ввод не терять.

Обязательные тексты:

| Ситуация | Сообщение |
| --- | --- |
| Пустое название после нормализации | «Введите название задачи» |
| Слишком длинное название | «Название должно содержать не больше 200 символов» |
| Некорректная дата | «Укажите корректную дату» |
| Реальная дата вне диапазона | «Выберите дату с 01.01.2000 по 31.12.2099» |
| Некорректное время | «Укажите время в формате ЧЧ:ММ» |
| Время без даты в некорректно сформированном вводе | «Для времени сначала укажите дату» |
| Дубликат | Тексты раздела 6 |
| Успешное редактирование | «Изменения сохранены» |

Ошибку поля очищать при изменении этого поля; окончательно проверять все поля при отправке. Ошибки хранилища не скрывать по таймеру: они остаются до успешной операции или загрузки. Сообщения об успехе показывать в ненавязчивой области `role="status"` на 4 секунды или до следующего действия. Важные ошибки сообщать через `role="alert"`; не выводить пользовательский текст и сырой JSON в console.

Никаких сообщений «Сохранено» до фактической успешной записи. Не использовать блокирующие `alert` для штатных ошибок; нативный confirm допускается только для удаления.

## 15. Дизайн и доступность

### 15.1. Визуальное направление

Согласованный характер — тёмный спокойный планировщик с дружелюбной подачей. Визуальный приоритет принадлежит задачам и вводу. Использовать графитовую основу, различимые тёмные поверхности, зелёный акцент и мягкие скругления. Одна тема без переключателя. Не применять постоянное неоновое свечение, яркие градиенты и крупные декоративные плашки, конкурирующие со списком.

Документ `Whats_Up_Bro_Visual_References_v1.0.docx` — источник визуального направления. Первое изображение описывает интерфейс, второе — характер бренда и Hoodie Bro. Настоящее ТЗ содержит необходимые правила самостоятельно: копирование композиции постера, демонстрационных подписей, цветных категорий и робота с первого изображения не требуется.

В прототипе использовать одну колонку по разделу 4. Изображение с тремя колонками не является мобильным макетом. Боковые панели, семь дней, прогресс и персонаж не добавляются в текущую поставку. Дружелюбный характер передают название и приветствие; подписи действий и ошибки остаются нейтральными.

### 15.2. Палитра и состояния

Для реализации зафиксирована следующая палитра. Это конкретизация принятого направления, а не точное извлечение цветов из иллюстраций.

| Назначение | Цвет |
| --- | --- |
| Фон страницы | `#111619` |
| Поверхность формы и карточек | `#1B2227` |
| Поверхность при наведении | `#242E33` |
| Декоративная граница карточек | `#39464E` |
| Граница полей ввода и вторичных кнопок | `#70818B` |
| Основной текст | `#F3F6F4` |
| Вторичный текст и подписи | `#B5C0C5` |
| Основной зелёный акцент | `#4ADE80` |
| Зелёный акцент при наведении | `#6EE7A0` |

Один основной зелёный используется для основной кнопки, отметки выполнения и индикатора фокуса. Эти состояния дополнительно различаются текстом, формой кнопки и checkbox. Не заливать зелёным все карточки и не выделять им каждую дату. Вторичные кнопки нейтральные, с различимой границей. Завтрашние задачи не окрашивать жёлтым: сам по себе следующий день не является предупреждением.

Просрочка обозначается текстом и цветом ошибки; выполненность — checkbox и читаемым приглушённым текстом. Карточка выполненной задачи не получает большую яркую заливку. При disabled-состоянии элемент визуально отличается, но его подпись остаётся читаемой. Ошибки не маскировать под зелёное подтверждение.

В будущих иллюстрациях лаймовый оттенок Hoodie Bro допустим как второстепенная деталь персонажа, а не второй равноправный цвет кнопок. Жёлтый можно использовать для реальных предупреждений при дальнейшем развитии, но новые предупреждения и дополнительные цветовые состояния в прототип не вводить.

### 15.3. Типографика, карточки и иконки

- Системный стек: `system-ui, -apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif`; внешние шрифты не загружать. Один шрифт интерфейса, без рукописных подписей в задачах и элементах управления.
- Основной текст — 16px, межстрочный интервал 1.5; подписи и вторичные данные — не менее 14px. Поля на iPhone — не менее 16px, чтобы избежать автоматического увеличения при фокусе.
- Название продукта — 32px на широком экране и 28px на узком, вес 700; заголовки групп — 18px и вес 600. Название не должно занимать половину первого экрана.
- Карточки задач — радиус 14px, внутренние отступы 16px, расстояние между карточками 12px, между группами 24px. Поля и кнопки — радиус 10px. Длинный текст увеличивает высоту карточки без фиксированного ограничения.
- Использовать сдержанные границы и различие поверхностей; тени не обязательны. Избегать сильного размытия фона и текстур, ухудшающих чтение.
- Если нужны иконки, использовать единый контурный стиль: встроенный SVG с областью 24×24, толщиной линии 2 и скруглёнными концами; видимый размер около 20px. Не смешивать эмодзи, объёмные картинки и разные наборы значков в управлении. Нативные checkbox остаются допустимыми.
- Иконки не заменяют понятные подписи «Добавить», «Сохранить», «Изменить», «Удалить». Декоративные SVG скрыть от скринридера, не создавая дублирующих имён.

### 15.4. Адаптивность и доступность

- Ширина основного контейнера до 880px, по центру; горизонтальные поля минимум 16px. На узком экране поля и кнопки переносятся без горизонтального скролла.
- Проверять ширины 320, 390, 768 и 1440 CSS px; масштаб браузера 200% не скрывает функции.
- Интерактивные зоны минимум 44×44 CSS px. Кнопки работают касанием и клавиатурой, hover не является условием доступа.
- Видимый фокус, логичный Tab-порядок, нативные кнопки и checkbox, доступные имена вроде «Удалить задачу: {название}».
- Сворачивание выполненных — кнопка с `aria-expanded`/`aria-controls` или корректный нативный `details/summary`; недоступные скрытые элементы исключены из Tab-порядка.
- Цвет не единственный признак просрочки, ошибки или выполнения. У выполненной задачи checkbox отмечен, текст визуально приглушён, но остаётся читаемым.
- Контраст обычного текста не ниже WCAG AA 4.5:1; границы активных элементов управления и индикатор фокуса — не ниже 3:1 относительно прилегающей поверхности. Декоративная граница карточки не заменяет границу поля. Проверить фактические сочетания, включая hover, а не считать заданную палитру автоматической проверкой.
- Язык документа `ru`, UTF-8, корректный viewport без запрета пользовательского масштабирования.
- Маскот, декоративные изображения, сложная анимация и звуки отсутствуют.

### 15.5. Визуальное развитие после прототипа

При отдельном переходе к полному MVP сохранить общее визуальное направление, но проектировать компоновку для компьютера и телефона отдельно. Трёхколоночный интерфейс не уменьшать механически до ширины телефона. Список задач остаётся главным центром внимания; вспомогательные панели, мотивационные сообщения и прогресс оформляются спокойнее.

Для будущего маскота выбран Hoodie Bro: тёмная толстовка и кепка, дружелюбная мимика, ярко-зелёные детали. Другого робота с первого изображения не использовать. До внедрения понадобятся отдельные изображения персонажа с прозрачным фоном, без надписей постера и мелких деталей, теряющихся в компактной карточке. Это требование к будущим ассетам, не задача на их создание сейчас. Раздел не расширяет объём раздела 19.

## 16. Указания для разработчика

### 16.1. Нормализация названий

Сохраняемое название: `rawTitle.trim().replace(/\s+/gu, ' ')`. Длину после нормализации считать как `Array.from(title).length`, не как число UTF-16 code units. Не полагаться исключительно на нативный `maxlength`, если он не соответствует этому правилу.

Ключ уникальности: `title.toLocaleLowerCase('ru-RU')`, где `title` уже нормализован. Не выполнять NFKC, транслитерацию, замену «ё» на «е» и удаление пунктуации. Ключ вычисляется для сравнения и не хранится отдельным полем.

### 16.2. Безопасность

Любой текст задачи выводить через `textContent`/текстовые DOM-узлы. Не подставлять пользовательские строки в `innerHTML`, HTML-атрибуты через конкатенацию или исполняемый код. Не использовать `eval` и `new Function`. Строка `<img src=x onerror=alert(1)>` должна отображаться как текст.

### 16.3. Организация и тестируемость

В `prototype/script.js` логически разделить функции работы с хранилищем, валидации, дат/сортировки, операций и DOM. Дополнительные JS-файлы приложения не создавать. Должен быть один источник состояния в памяти; DOM не использовать как базу данных. Слушатели и таймеры не должны дублироваться после рендера.

Чистые функции должны запускаться без DOM: экспортировать их через `module.exports` только при наличии CommonJS-окружения; браузерная инициализация выполняется только при наличии `document`. Это позволяет тестам через `require('../prototype/script.js')` проверять реальную реализацию, не копируя её. В браузере скрипт остаётся обычным, без модулей и сборки. Передавать текущую дату/время в функции группировки аргументом, а не фиксировать глобальные часы внутри них.

Случайные id не зависят от названия задачи и остаются неизменными при всех правках. Если оба криптографических API недоступны, показать понятную ошибку невозможности создания, а не генерировать заведомо конфликтующие id. Поддерживаемые современные браузеры предоставляют `getRandomValues`.

Не требовать функций браузера, недоступных в одном из целевых браузеров, без рабочего fallback. Обновление списка не должно пересоздавать форму или терять курсор и выделение при фоновом пересчёте даты. Не перехватывать системные сочетания клавиш браузера.

### 16.4. Проверка актуальности хранилища

Хранить точную исходную строку `lastLoadedRaw`, включая `null` для отсутствующего ключа. Перед `setItem` выполнить `getItem` и сравнить результат с `lastLoadedRaw`. Ошибка чтения означает отказ операции; несовпадение означает конфликт по разделу 13.3. При успехе записи обновить `lastLoadedRaw` строкой, которая фактически записана. При ошибке не менять ни её, ни подтверждённое состояние задач. При явной повторной загрузке заменить её вновь прочитанной строкой.

## 17. Запуск и платформы

Основной пользовательский способ запуска на всех целевых устройствах — один постоянный HTTPS-адрес статического размещения содержимого `prototype/`. Статический хостинг только отдаёт HTML, CSS и JS, не хранит задачи и не добавляет серверную логику. Использовать относительные пути между тремя файлами. Один адрес устраняет путаницу разных способов запуска, но не синхронизирует localStorage между устройствами и браузерами.

Для локальной разработки допустимы статический HTTP-сервер с каталогом `prototype/` и открытие `prototype/index.html` двойным щелчком. Запуск через `file://` — дополнительный режим без обещания одинакового поведения localStorage в Chrome и Firefox. Он не является основным пользовательским способом и не заменяет HTTPS-проверку. Не требовать открытия HTML из iOS Files как надёжного браузерного приложения.

`file://`, `http://` и `https://`, разные порты и домены имеют разные контексты хранения; для `file://` поведение зависит от браузера. Не обещать общий список между ними. Если localStorage запрещён настройками или недоступен для выбранного способа открытия, отработать ошибку раздела 13.

### 17.1. Предпосылка проверки HTTPS

Для браузерной приёмки нужен реально предоставленный HTTPS-адрес. На момент этого ТЗ адрес не выбран, размещение не выполнено. Рекомендация — Cloudflare Pages со статическим каталогом публикации `prototype/` и без команды сборки; другой статический HTTPS-хостинг подходит при тех же условиях. Доступ сервиса к репозиторию и публичность страницы определяются отдельно при размещении, а не подразумеваются этим документом. Учётные данные не включать в исходники и ТЗ.

Выбор аккаунта/провайдера и команда на публикацию нужны только перед размещением. Отсутствие адреса не блокирует написание трёх файлов, автоматические тесты и локальные браузерные проверки. Оно блокирует финальную HTTPS-приёмку, особенно реальный iPhone: пометить соответствующие проверки «не запускалось: нет HTTPS-адреса», не объявлять полную поддержку проверенной. Полной публикации и проверки iPhone нельзя подменять планом.

### 17.2. Браузерная проверка и срок хранения

На Windows проверить актуальные стабильные Chrome и Firefox, на iPhone — Safari. Основной браузерный прогон после размещения выполняется по одному HTTPS-адресу.

На iPhone проверить реальный Safari, включая нативные поля даты/времени, клавиатуру, касания, прокрутку и восстановление после сворачивания браузера. Эмуляция мобильного viewport на компьютере не заменяет эту проверку. В отчёте фиксировать реально проверенные версии браузеров/ОС; непроверенный iPhone явно отмечать как непроверенный, а не как прошедший тест.

Хранение в браузере не бессрочно и не равно резервной копии. Safari/WebKit, в том числе механизмы защиты от отслеживания, настройки приватности и очистка данных браузером могут ограничивать срок хранения и удалять данные сайта. Упоминаемые для отдельных условий ограничения в семь дней нельзя трактовать как универсальное правило для любого Safari и любого способа использования. Прототип не обходит политику браузера и не обещает определённый срок сохранности. Проверить обычный режим на реальном iPhone, повторное открытие и состояние после очистки данных; долгосрочную сохранность, если её не проверяли, отметить как непроверенную. Удалённое браузером хранилище неотличимо для приложения от первого запуска: не обещать обнаружение или восстановление пропавших записей.

После получения трёх файлов работа с задачами не требует Интернета. Это не обещание доступности заново открываемого HTTPS-сайта офлайн: service worker и PWA не входят в прототип.

Проверки ошибок выполнять в изолированном тестовом профиле/контексте, не разрушая пользовательское хранилище. Для времени и отказов хранилища допустимы тестовые подмены через браузерные инструменты или внешний тестовый harness, но не постоянные тестовые переключатели в продукте.

### 18.1. Обязательные автоматические тесты

При реализации создать `tests/*.test.cjs` на встроенных `node:test` и `node:assert/strict`. Запуск из корня репозитория: `node --test`, Node.js 22 или новее. Пакеты, package.json и сборка для этого не нужны. Тесты не входят в три файла приложения, не публикуются как часть каталога `prototype/` и не добавляют требований к браузерному запуску.

Проверять реальные функции из `prototype/script.js` по разделу 16.3. Обязательное покрытие:

- Нормализация, длина, уникальность, исключение собственного id и запрет совпадения с выполненной записью.
- Валидные/невалидные поля и JSON, дубликаты id, неизвестная версия/поле, время без даты и границы диапазона дат.
- Просрочка до/в момент срока, дата без времени, смена дня, месяца, года и високосный день.
- Порядок групп и карточек, отсутствие дублирования в группах, независимость календарных дат от UTC.
- Обновления той же записи без смены id, отмена/отсутствие изменений без записи и неизменность подтверждённого состояния при отказе сохранения. Логику записи организовать с передаваемым адаптером хранилища, чтобы имитировать отказы и внешний конфликт без браузерных данных пользователя.

Каждый тест фиксирует конкретное ожидаемое поведение из таблицы AT; не копировать реализацию в тесты и не заменять ожидаемый результат вызовом той же функции. В отчёте указать соответствующие AT и число реально выполненных тестов. Автотесты чистых функций не заменяют проверку DOM, фокуса и реального Safari. Результаты фиксировать раздельно: пройдено, не пройдено, не запускалось. В настоящем документе эти проверки ещё не выполнены.

## 19. Что не входит в прототип

AI, OpenAI, голос, серверный посредник, регистрация, аккаунты, синхронизация, заметки, отдельный календарь, приоритеты, категории, поиск, фильтры, повторения, массовые действия, drag-and-drop, напоминания, системные уведомления, PWA, push, маскот, импорт/экспорт, архив, корзина и отмена после удаления.

Не делать пустые разделы и кнопки-заглушки под эти возможности. Не создавать «умный» разбор фраз: «завтра в 10 позвонить» в названии остаётся обычным текстом, срок задаётся полями.

В прототипе нет регулярного резервного копирования и восстановления. Исключение из запрета экспорта — только аварийное копирование исходной строки при ошибке загрузки (раздел 13.1), без импорта и исправления данных внутри приложения. Использовать тестовые записи; штатный экспорт/импорт планируется отдельно перед переходом к важным данным. Safari и другие браузеры могут удалить локальные данные по собственным правилам; исключения или гарантии хранения для iPhone не обещаются (раздел 17.2).

## 20. Готовность и дальнейшее действие

Локальная реализация завершена после создания трёх файлов в `prototype/`, прохождения обязательных автотестов и доступных локальных функциональных проверок с отчётом о результатах и ограничениях. Полная браузерная приёмка дополнительно требует HTTPS-прогона на Windows Chrome/Firefox и реальном iPhone Safari. При отсутствии адреса или устройства локальная часть может быть завершена, но полная приёмка остаётся незавершённой. Нельзя заявлять проверенную поддержку реального iPhone по одному настольному эмулятору.

Само это ТЗ не является командой на написание кода, публикацию, создание PR или слияние. Текущий результат — обновлённый `tz.md`; реализация начинается после отдельного запроса пользователя.
